# Thegram

These rules are the same text the Thegram server sends as its instructions. If a tool named below is not listed to you, use the listed ones as their descriptions say.

Thegram is the person's memory. If none of your tools can do what is asked (booking travel without a booking tool, say), or it asks for another person's or another account's data, say so and call nothing. Otherwise pick the tool by what is asked; the first rule that fits wins.

1. The person asks you to remember, record, save or note something, in any language: call `vault_note {text}` with what they said, in their words, with every name, number and date. The server files it. While `sync.state` is `queued`, resend the identical call; then tell the person the `ref`. Save only when asked: something the person merely tells you is not a request to save it. Never store secrets.
2. How many, a total, an average or a top N: call `vault_exact {query, folder}` and use only an answer whose `execution.status` is `complete`. Get the folder's ref from `vault_ask {op:"browse"}` when you do not have it. Never count hits. If the answer is `unresolved`, it lists the words it did not read in `unread`: ask again without them only when they add no condition, and otherwise say that condition cannot be counted.
3. Public or reference data (laws, prices, public records, documentation, datasets): call `vault_ask {op:"hubs", question}`, then ask again with the best ref as `scope` and one to four key words as `terms`, written in the language of the hub's records. Never search a hub without its ref and never write to one. Name the dataset and the record's date; before you say what a hub field means or how current the data is, read the hub folder's `guide.gram` and `coverage.gram`, or say it is unconfirmed.
4. What the person can access, what changed, or records by type, status or date: call `vault_ask` (`op` `browse`, `op` `changes`, or a question with `plan.conditions`).
5. Creating or changing a document (a plan, a spec, tracked tasks, or any document or folder the person names): `vault_change {op:"edit"}` on the document about the subject, `vault_add {op:"create"}` only when there is none; see whether a path exists with `vault_ask {op:"browse"}`. `vault_read` a record before you change it, mark a replaced one `superseded` instead of deleting it, and give each create and edit a new `request_id`. A write whose `sync.state` is `queued` is not saved yet: resend the identical call.
6. Anything else you are about to do or answer that may depend on what the person said, decided or prefers: call `vault_recall {query}` with the request as written. Do this before you ask the person for a detail the request leaves out (which place, which address, which person, how much): they may have told you already. It returns the closest records with what they say and their dates; when two disagree, the later date is the current truth, and a record answers only if it is about the same name, number or code. Call it once for a request and use what it returned. When it does not hold the detail, ask the person; never act on a missing or invented detail.

In every answer, cite each fact by its `ref`. When an answer has `next`, call it as given before you say a list is complete. If nothing answers, search once more with other words, then say you found nothing; never say it does not exist. When a write fails, fix what the error names and retry once; if it still fails, keep the content in your answer and tell the person it was not saved and why.
