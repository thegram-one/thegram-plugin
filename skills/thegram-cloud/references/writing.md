# Write and maintain one deeply researched document

Use this method for any authorized document: a research subject, explanation, specification, plan, project or everyday concern. The deliverable is a coherent, useful account of the subject, not a search-result digest, copied AI answer or pile of source summaries. Its prose explains the subject; its typed records preserve the facts, claims, evidence and relationships; its revisions preserve how that understanding changed. A broad research-and-save request calls for an extensive reference account, not a quick overview. Respect an explicitly brief, sampled or narrowly scoped request instead of expanding it.

Contents: 1 Establish the document and the question · 2 Build and execute a research task plan · 3 Preserve source identity and meaning · 4 Write the subject, not the search log (long documents, body rules) · 5 Preserve time · 6 Checkpoint and update · 7 Verify usefulness, coverage and continuity

## 1. Establish the document and the question

Start in the same turn. Infer what context supplies; never ask for exports or information a connected source can answer.

1. Identify the subject, the questions the document must answer, the requested period and exclusions. A keyword is a starting point, not permission to collect everything containing it. Respect a requested time range; use the full history when requested or necessary to explain the subject. Do not silently substitute recent material, representative examples or an arbitrary small source set for a broad request. State any inferred boundary and why it fits the purpose; a connector limit does not redefine the requested scope.
2. Reuse the explicitly named or established document in the authorized destination. For personal writing without an established destination, resolve [the person root](person-vault.md), then inspect its documents and relevant records for this subject, including moved or renamed paths. Continue an existing `projects/<slug>.gram` as it is; do not migrate or duplicate it. Only a genuinely new subject gets `<root>/<subject-slug>.gram`. Keep the path stable even if the title changes. Create folders or move documents only when asked.
3. Read its brief, outline, relevant sections, root record, source identities and latest run/coverage records. Follow pagination. Existing prose and facts are the starting understanding, not replacements for inspecting changed sources.
4. Use the sources the request names or clearly covers among the host's connected tools: repositories, documents, chats and mail, calendars, trackers, and the web or publications when available. Search the subject's name, aliases and related terms in the person's languages within those sources.
5. State the subject, initial source/window scope and one destination path briefly, then work. Ask only for a material ambiguity that the context and sources cannot resolve.

Saving must be authorized (SKILL.md section 1). A request to research or answer without saving remains read-only. Never create a source-inbox document, a second progress file or any other side document.

## 2. Build and execute a research task plan

Before substantive collection, turn the request and existing context into a working plan. A bounded reconnaissance may identify the main questions and source families, but it is not the finished investigation. For a broad subject, cover its defining concepts, major parts and mechanisms, relevant evolution, competing explanations or approaches, evidence and counterevidence, limitations and practical implications as applicable. Tailor these dimensions to the subject; do not force irrelevant categories or a fixed task count.

### Tasks are the execution contract

1. Create concrete research tasks for the substantive questions and coverage areas, not just "search, summarize, save." Each task has an answerable question, relevant connectors/source families and window, the explanation or comparison it will add, dependencies if any, and observable completion evidence. A large task splits into independently verifiable subquestions or time ranges. Do not enumerate every possible source item before starting.
2. Track the plan with the host's task facility when available. For authorized saving, persist it as real `task` records in the same subject document, tagged `research-work` and linked `part-of` its root. `owner` is the actual researching assistant, not the person. Put question, scope, expected output, acceptance, progress and next action in `d`; use only supported fields. Reuse IDs across units and sessions. These are current work delegated by the research request, not invented historical tasks, source PR tasks or newly assigned product work.
3. In an existing document, save the initial plan with fresh write preconditions before substantive collection. In a new document, plan first, inspect one bounded source unit, then save the plan with that unit's substantive prose and facts in the initial create. For deliberate historical reconstruction, retain the plan in the host until the first permitted historical batch rather than advancing `effective_at` just to save a plan; task `start`/`done` still describe the actual research execution, not fictional past work. Do not create a separate plan document or an empty shell. Read-only research keeps the plan in the host/session without writing records.
4. Use `open` for queued tasks and `active` only for work actually underway. Use `depends` for real prerequisites, and continue independent tasks while one is blocked. Keep the task stable while it consumes many PRs, weeks or sources; the coverage checkpoint tracks those units, not a new task for every search call or record.
5. After every unit, reconcile the task's questions with the evidence. New mechanisms, contradictions, missing periods, referenced primary sources and justified related keywords create or refine research tasks. Follow relevant connector links across source families instead of treating the first convenient connector as sufficient. Do not add unrelated scope merely to make the plan large.
6. Complete a task only when its planned material has been inspected, its question has a supported answer or an explicitly evidenced unresolved result, its promised explanation is saved and read back, and its coverage is accounted for. A snippet, introductory summary, source count, successful write, finished run or task list is not completion evidence. A genuinely unsettled question can be a research result after adequate investigation; an unread accessible source or unperformed check is unfinished work.
7. Keep reachable unfinished tasks moving in the same execution. Do not end after the first useful batch, ask whether to continue already authorized work, or turn required remaining research into optional "next steps." A real access/runtime limit or user stop may interrupt the work: save the exact remaining scope and next unit; mark the affected tasks `blocked`, `waiting` only for an actual user decision, or `open` when merely queued for resumption. Do not claim background continuation unless a real authorized job exists. Creating task records does not schedule jobs, send reminders or authorize delegation.

### Bounded units control batch size, not research depth

Repeat small read–reconcile–write units until the task plan's completion criteria are met. A PR, thread, section or week is a processing unit, not the total research allowance. Do not inventory all history before the first useful write or stop merely because the first units yielded a plausible overview.

1. Start with a manageable unit: one PR/issue and its discussion, one conversation or mail thread, one document section, or a week of activity. For dated history, begin at the earliest requested or discoverable boundary and advance. For a conceptual investigation, begin with a question and relevant primary sources rather than arbitrary dates.
2. Finish every page within that unit. If results are truncated, dense or exceed what can be read and reconciled together, narrow by day, channel, repository, item or subquestion. Widen sparse windows when useful. A result limit is not the end of the source; leave an explicit gap if the connector cannot expose more.
3. Within a time window, check all relevant authorized connectors before calling that window covered. Read a PR's description, diff, commits, reviews and outcome; a thread's relevant replies; a document's applicable sections and revision. A search snippet or title locates material but does not establish its full meaning.
4. Follow meaningful connections: an alias, prior name, cited document, linked issue, participant's explanation, disputed claim or missing prerequisite. Record why an added search belongs to the subject. Do not drift into unrelated people, projects or private material merely because a connector exposes them.
5. For each relevant inspected item retain its stable identity, permalink when available, source dates and precision, inspected version/update marker, and what it establishes. Distinguish discovered-but-unread items from inspected items and durably written items. The working inventory covers this unit, not the entire research universe.
6. After the unit, ask what the evidence explains, contradicts or leaves unanswered. Update the research tasks and choose the next ready unit. An unresolved question may warrant work by the researching assistant; it never automatically becomes a task assigned to the person.

A request for an entire repository's history still covers every default-branch commit (including commits outside PRs), PR in every state, issue, release and tag within that scope. Partition the enumeration; do not sample it or silently replace it with selected highlights. Compare counts only against source totals with the same repository, branch, period and item kinds. Keyword search in chats or mail rarely proves exhaustive coverage: report the queries and limits, not "all conversations found."

## 3. Preserve source identity and meaning

Read [record meanings](record-meanings.md) for classification and [knowledge-model.md](knowledge-model.md) for basis, reasoning links and pinned provenance. Use all 22 types when their meanings are present, never a quota or a default type for every result.

| Material | Stable identity and what to inspect |
|---|---|
| GitHub or another repository | host and owner/repository plus full commit SHA, PR/issue number, release ID/tag; body, diff, review, state changes and relevant follow-ups |
| Conversation | conversation ID or shared link and its date; relevant messages, the person's corrections and actual outcome; an AI explanation is not independent verification |
| Slack or another chat | workspace/channel plus thread/message ID; relevant replies and later corrections |
| Mail | account scope plus thread/message ID; relevant replies, commitments and outcomes |
| Document, paper or web page | provider/file ID, DOI or canonical URL; version/date and section or page locator for each supported claim |
| Calendar or tracker | account/calendar/project plus item ID; recurring events also need the occurrence identity |

Reuse existing IDs by source identity/permalink before deriving new ones. New IDs use only lower-case ASCII letters, digits and hyphens and include enough namespace to avoid collisions. Do not strip characters from opaque IDs or truncate them if that could merge different items; use a stable safe encoding/digest when available, otherwise persist a short unique mapping to the exact identity in the source's `d`. Missing identifiers stay missing: do not merge two conversations only because their dates and subjects resemble each other. Explain uncertain identity and reconcile it before adding a possible duplicate.

- Every relevant inspected item gets one `source`, including low-signal material with no domain fact. Its `d` retains exact identity, dates, inspected version, locator and scope; `ref` holds one real openable URL, not a fabricated address. Use `tag` `source:<connector>` and `source` fields on supported records.
- An item and the facts it establishes are saved together. Never import only sources first and postpone all their facts until the end. If one item needs several writes, mark its coverage partial and save each source fragment with its facts before declaring that version processed.
- A repeated fact is one record with all supporting sources, not one record per connector. Reuse components by responsibility, tasks by tracked work, and metrics by quantity/definition/unit. Strengthen or correct their explanations as new material arrives.
- A commit is provenance, not automatically an event or task. Read its diff for decisions, components, constraints and evidence; a routine change may retain only its source.
- A PR or issue represents tracked work. A PR is `active` while draft, `review` while ready for review, `completed` when merged, `cancelled` when closed unmerged; preserve sourced opening/finish dates. An issue closes according to its stated outcome, not merely because a related commit exists. A release has its source and publication event; a downloadable asset also warrants an artifact with its real URL. A bare tag is not proof of a published release.
- Distinguish the source's assertion, observed evidence and this author's synthesis. A useful inference states its premises, limits and unverified status in prose and `d`, carries `basis:inferred` and has `supports` links from its premises; an untested planning premise is an `assumption`. Never turn an AI recommendation into an accepted decision or an AI explanation into verified evidence.
- Preserve disagreement with scoped claims and supporting/contradicting evidence. Different versions, populations or measurement windows may explain a conflict; do not average incompatible findings or treat repeated copies of one source as independent confirmation. Sequence alone does not prove causation.

Connect claims with the reasoning links in [knowledge-model.md](knowledge-model.md) section 3: premises and evidence `supports` or `contradicts` the conclusions they argue for, work `implements` decisions only when shown, components `depends` on sourced dependencies, and records are `part-of` the document's purpose or another appropriate record. Avoid decorative links. Every record must be attributable and reachable from the root, through a meaningful link or its source.

## 4. Write the subject, not the search log

Choose an outline that answers this subject's questions. Explain context and terms, mechanisms and relationships, alternatives and tradeoffs, evidence and limitations where they matter. Do not impose a fixed project template or headings per month, connector, PR or search batch. Chronological sections are appropriate only when chronology itself explains the subject. Set the title in document metadata; begin the body with a localized content section, not a repeated document title or leading root-title card.

Write enough detail to be useful without reopening every source: how the parts relate, why a conclusion follows, conditions under which it holds, exceptions, practical implications and unresolved questions. Each major research question needs a developed, source-supported explanation, not a sentence under a heading. Compare alternatives by their mechanisms, assumptions, evidence, tradeoffs and applicability where relevant. Retain concrete examples or measurements when sources support them. Let the amount of material determine the document's size; do not compress a broad investigation into an executive summary. Depth comes from explanation and coverage, not padding, repeated summaries, keyword lists or quotas for words, elapsed time, sources, tasks or record types.

1. Create the document once, after the first useful unit: `gram_create` with `base_revision:null`, the metadata title, a scoped overview, the first substantive section, a root `project` record (`prj-<subject>`, `x:active`), the research task plan and that unit's sources and facts. The root groups the writing purpose; it does not assert a real-world project exists. If nothing could be inspected, report the limit instead of creating an empty shell.
2. Continue section by section with `gram_patch`; use the section-by-section contract below. Sources, facts and their narrative belong to the same coherent write when they fit. Otherwise finish the affected sections before marking the unit complete. Use at most about 20 source items, 60 operations and 8,000 characters per call, or the lower advertised limit; split at a semantic boundary.
3. Use one primary readable representation per fact: prose for explanation, a table for comparisons, a list for steps. Cite supporting records or sources beside the claim, and place a domain record at most once where a card actually helps. Keep the full inventory in records/checkpoints and only necessary citations near the end; do not flood the body with an unbounded source collection. Do not copy raw transcripts, message bodies or reports unless the person explicitly requests a scoped source capture; never store secrets.
4. When new evidence changes the understanding, rewrite the affected section and existing records, preserving still-valid facts, caveats and source links. Do not append a contradictory "latest update" below an obsolete conclusion. Retain the former state in revision history; do not delete a once-true record to hide it.
5. Read existing sections with `source:true`, finish that snapshot's pages, and use its `doc.rev`/`doc.hash` for replacement. `set`/`unset` uses the actual `old`. Reconcile concurrent changes before retrying; never attach fresh tokens to an old draft.

The selected revision's body is its current knowledge state. Old still-valid explanations, requirements and accepted decisions remain useful; dated activity reports, prior outputs and completed work are not automatically current knowledge. Retain historical facts in records and native versions instead of making monthly body logs. A current measurement, future appointment or verification result may need authored prose/table because its record card can be hidden by the host.

Apply actual type/status eligibility without inventing visibility fields. Closed records stay in the record list/history; done tasks, goals, blockers and risks leave current-work sections, while an accepted decision can remain valid. After a status transition, reconcile authored rows and eligible project/goal descriptions too: the UI cannot remove stale Markdown for you. Preserve source captures and explicitly requested retrospectives rather than censoring their history. Never retype valid records just to force display.

Use only the host's real rendering and presentation controls. Do not invent collection pagination, collapse attributes or dashboard settings. Saving records does not prove lazy rendering, a particular layout or visible cards.

### Long documents: write section by section

A long explanation, architecture document, spec, review, report or manual is saved in steps, never as one oversized call:

1. Plan the outline with a metadata title, localized `##` content sections and `###` subsections. Headings are unique, so each section can be found again; do not repeat the host's title as a body heading or root-title card.
2. `gram_create` once the first source unit is understood, with a metadata title, scoped overview, first substantive section, root record, the research task plan and that unit's sources and facts. Plan before collection; do not create an empty shell before reading.
3. One `gram_patch` per `##` section: `{"op":"section","heading":"## 3. Storage","text":"<Markdown under the heading, its ### subsections included>"}`. A missing section is added at the end; an existing one is replaced up to the next `##`. Keep each call under about 8,000 characters; split a bigger section into `###` sections written one per call.
4. Records the section explains go in the same patch: `add` with `"place":"none"`, then natural inline citations or a single `[[id]]` placement where useful. A record card is not a substitute for the explanation.
5. Before replacing an existing section, read it with `gram_read {path, section:"3. Storage", source:true}` and retain that response's `doc.rev` and `doc.hash` with the text. Follow every `more` cursor to finish the same snapshot; on a stale cursor, restart the read. The stored Markdown preserves headings, tables, list markers, `[label](@id)` mentions and `[[id]]` lines. Edit it and send `gram_patch {path, request_id, base_revision:<that doc.rev>, expected_hash:<that doc.hash>, operations:[{op:"section",heading:"## 3. Storage",text:<edited text>}]}`. Never pair old text with tokens from a later brief or write receipt, omit the preconditions to force a write, or resend the plain read's rendered HTML. A one-sentence fix is an `edit-text`.
6. On a revision/hash conflict, reread the section and reconcile the intended change with the intervening edits; if they conflict in meaning, ask the person rather than choosing an overwrite. Submit the reconciled payload with the new read's tokens and a new `request_id`. For other errors, fix the named cause; sections already written stay. `E_NO_CHANGE` means the section already reads that way, not that another write succeeded.

Use headings, short paragraphs (three to six sentences), lists, tables, code blocks and `flowchart` diagrams; a paragraph is never a container for a list of facts.

### Body rules

- A status or overview paragraph states only the current state in a few sentences. When the state changes, rewrite that paragraph; never append the latest change to it. Growing an existing paragraph past 1,000 characters is refused (`E_LONG_PARAGRAPH`).
- Preserve meaningful dated changes in their proper records with source attribution. Explain them in the body only when they clarify the selected revision's current understanding or an explicitly requested retrospective; do not append a permanent activity feed.
- No lists of PR numbers, commit hashes, image digests or clock times in prose. One event per meaningful step, not one per PR or commit; group a batch of merged PRs into the one release or deployment they shipped in.
- A recurring writer (a scheduled run, a session hook) updates the same records and the same status paragraph each time; it never grows a running log in the body.

## 5. Preserve time without manufacturing history

Every meaningful write creates a real revision. `recorded_at` is always the server's actual recording time. Source occurrence dates, task dates and metric observation dates remain in their own fields at their known precision. Send `effective_at` as ISO 8601 with a zone and whole seconds, and compare it with the document's last boundary before writing.

- Ordinary research and updates express the understanding established now: use a current, nondecreasing `effective_at`, not an old source's date for a synthesis that uses later evidence.
- When the person asks to reconstruct history from its beginning, process bounded windows in chronological order across the relevant sources. Each write's `effective_at` is the latest supported boundary in that batch; add a fact in the first write that establishes it and update it when later sources change it. Only evidenced status transitions are replayed. Do not include present-day conclusions in an earlier revision.
- Never lower a document's last `effective_at`, rebuild it, or insert an earlier revision. An older fact discovered later is added at the current knowledge boundary, with its real dates and the late-discovery limitation stated. Undated claims cannot be assigned a fictional historical boundary. Future events are known now, not only on their future occurrence dates.
- A historical read selects revisions, not individual dates inside one batch. Do not promise within-batch precision or that a later-discovered fact appears in an earlier state.
- Each intended write has its own `request_id`, including a stable run identifier and unit/batch ordinal; two writes at the same effective time must not share an ID. Persist the pending unit when continuing a session. Retry a lost response with the identical payload and ID; for `E_REQUEST_REUSE`, inspect what landed instead of assuming the whole unit is complete or resending it blindly with a new ID.

## 6. Checkpoint and update the same document

Keep progress in this document, using supported `task`, `source` and `run` records rather than invented checkpoint fields or a second file. Tasks describe the outstanding work; sources describe inspected coverage; the run describes the actual execution. None substitutes for the others.

1. Reuse one scope `source` per connector/scope. Its `d` records the queries/aliases, filters and exact windows covered, last fully written unit, source version/update watermark, next page/item when usable, unread or partially written items, and access/truncation gaps. A cursor may expire; preserve enough scope and stable IDs to restart that window safely.
2. Keep one `run` per actual research session, linked `part-of` the root and `derives` the scope sources. Its `d` records inputs, source/window scope, new/updated items, conclusions changed, task IDs advanced, unresolved questions and the next work. Update that run and the affected research tasks at each completed unit in the same patch as the final facts/prose and scope checkpoint. Use `done` only when the task's acceptance criteria are met, and rewrite its `d` with the outcome and retained coverage evidence. No separate run per search call. Reuse an existing run when resuming that execution; a new session gets a new run but keeps the same task and coverage IDs.
3. Mark a unit complete only after all its relevant items, facts and affected narrative are durably saved (`sync.state:synced`). A source ID alone is not proof its latest version or all its facts were processed. If interrupted mid-unit, reread the saved records and partial scope, then reconcile the remainder before advancing.
4. On the next requested update, read the research tasks, latest run, coverage and relevant source versions first. Search only new windows, pending gaps, changed known items and newly justified aliases. Reopen an existing research task when its answer or acceptance needs rechecking, removing its old `done` with the correct `old` value; add a task only for genuinely new work. Query by source update time or recheck mutable open items; creation dates alone miss an old PR merging or a document being revised.
5. Newly discovered keywords or a newly available connector may require an older window. Record that scope expansion and use the late-fact rule; do not treat the document's last effective time as a completeness watermark. Reinspect unchanged old material only when needed to resolve a new question or uncertain prior processing, not as a full rerun.
6. If no domain fact changed, leave those records and prose unchanged. Record only the actual check and its coverage in the run/scope records. A requested update never means duplicating the document, reimporting sources or rewriting every section.

## 7. Verify usefulness, coverage and continuity

Before reporting research completion, audit the task plan against the original request and discovered relevant questions. Run the logic audit in [knowledge-model.md](knowledge-model.md) section 9 on the same saved state. Every required task must meet its acceptance criteria; do not omit, cancel or narrow tasks just to finish. For an enumerable scope, account for every in-scope item and page. For an open-ended subject, demonstrate coverage of its material questions, relevant source families and competing positions, inspect the consequential follow-up leads, and record why further reachable leads do not materially change the explanation. A first search page or repeated copies of the same claim cannot establish this boundary.

1. Read back the saved sections and representative records. Does the document explain the subject and answer its questions, with conditions and limitations, rather than list what each source said? Do narrative and records agree? Inspect the title, table of contents, current-work rows and any automatically appended records; a clean authored paragraph is insufficient if old activity cards or stale descriptions still dominate. When the app is available, inspect the actual reading surface; otherwise report body readback separately from unverified rendering.
2. Check the unit inventory against saved source identities/versions and facts. Account for every relevant inspected item, including source-only items, and distinguish completed windows from partial, unread, inaccessible or unsearched scope. Compare exact totals only when the connector supplies a matching exhaustive enumeration.
3. Check stable IDs, sourced statuses/dates, source attribution and meaningful paths to the root. In a repository-history scope, account for PR/issue tasks and release events/assets as well as commits; do not use record counts as a richness target.
4. Verify one or two natural questions through retrieval and open the returned records or sections (SKILL.md section 9). Separate successful storage/readback from unverified retrieval or UI rendering.
5. For deliberate historical reconstruction, inspect an earlier and later state and the revision sequence: effective boundaries never decrease, earlier states exclude later additions, and supported status changes appear at their written boundary. Ordinary writing must still preserve earlier revisions without pretending to have reconstructed the past.
6. Report the single document path, what it now explains, material additions/corrections, task outcomes, inspected scope and remaining gaps. Distinguish storage success, task completion and completion of the overall investigation. Disclosing a limitation does not complete the blocked work. If required tasks remain because of a real limit or user stop, label the result partial, retain those tasks and give the exact next task/unit and resumption prerequisite; do not say "research complete." Unsearched accessible scope must be worked before yielding, not merely disclosed.
